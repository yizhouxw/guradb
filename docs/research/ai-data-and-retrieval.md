# AI 数据与检索产品调研

状态：调研结论与设计建议，尚未形成组件选型决定。核验日期：2026-10-17。

本文依据官方文档与规范分析 Lance/LanceDB、Milvus、Qdrant、Weaviate，服务于 GuraDB 产品与技术架构设计。
所有 GuraDB 能力均为设计目标；本轮没有部署这些产品，也没有验证其性能、故障行为或格式兼容性。
“官方文档描述”表示文档可查的行为或架构；“判断／建议”表示本项目据此形成的推论。

## 1. 调研结论

1. **对象存储上的多模态湖与检索已经是竞争交汇点。** LanceDB 已将训练、特征工程和检索纳入产品定位；Milvus 3.0.x 已提供外部湖数据的索引查询路径。因此，“对象存储 + 向量检索”不足以构成差异化。[LanceDB 产品文档](https://docs.lancedb.com/)、[Milvus 外部集合](https://milvus.io/docs/create-an-external-collection.md)
2. **训练数据访问应作为独立的产品能力。** SQL 扫描与 Top-K 检索不能完整表达样本混洗、跨 worker 分片、固定版本和恢复位置。LanceDB 已提供专门的训练加载器与版本绑定机制，值得作为直接参照。[训练数据加载](https://docs.lancedb.com/training/data-loading)
3. **检索一体化的重点是共同语义。** 向量、全文、关系扩展必须共享资产身份、源快照、权限、删除规则和查询预算，不能只在应用层拼接多个返回列表。这是 GuraDB 的建议设计方向。
4. **放弃高并发 OLTP 可明显收敛数据面，但不能取消正确性。** 建议围绕批量／微批提交、快照发布、异步索引与可复现数据集设计；控制面的提交、任务归属及权限仍需明确的一致性机制。
5. **差异化应验证完整流程。** 建议定位为“面向 AI 数据生命周期的开放多模态湖数据库”，重点验证 PostgreSQL 风格 SQL、跨格式版本治理、训练读取和有界图检索如何在同一数据身份体系内协同；这些仍是待验证假设。

## 3. Lance 与 LanceDB：最接近训练和检索共用数据的参照

### 官方文档描述

- Lance 支持列投影、过滤下推、分批扫描和 `take` 随机读取；这些分别服务于裁剪读取、流式批处理及训练抽样。[Lance 读写接口](https://lance.org/guide/read_and_write/)
- Lance 的写入形成新版本；删除可使用单独的删除索引，避免立即重写数据文件。调用方需要遵守表版本的读取语义。[Lance 读写与删除](https://lance.org/guide/read_and_write/)
- LanceDB 训练加载器提供混洗；其 `Permutation` 按构建时的表版本绑定读取，后续追加的行不会自动进入原有排列。这比“训练过程中不断读取最新表”更接近可复现的数据集语义。[训练排列与版本固定](https://docs.lancedb.com/training/data-loading)
- 官方区分单阶段逐行混洗与分块策略，明确完全随机读取可能降低吞吐。随机性与 I/O 局部性之间存在需要暴露和测试的取舍。[训练数据加载](https://docs.lancedb.com/training/data-loading)
- Enterprise 将持久表数据、manifest 和索引放入对象存储，后台索引／压实与请求服务分开；这是 Enterprise 架构描述，不能由此证明 OSS 嵌入式库具备同样的分布式调度能力。[Enterprise 架构](https://docs.lancedb.com/enterprise/architecture)
- 新数据尚未进入全文或向量索引时，LanceDB 文档描述通过既有索引与新增数据的穷举搜索合并结果；Enterprise 在后台异步更新索引。这保留覆盖范围，同时可能增加查询成本。[增量索引](https://docs.lancedb.com/indexing/reindexing)
- `read_consistency_interval` 控制读取检查其他写入者更新的频率；它与索引覆盖范围是不同维度。其远程表也有相应新鲜度约束。[读取一致性](https://docs.lancedb.com/tables/consistency)
- Lance 分别管理元数据缓存和索引缓存；manifest、删除文件、行标识映射等缓存键包含相应数据集／版本信息。[性能与缓存说明](https://lance.org/guide/performance/)

### 对本项目的判断

应借鉴“稳定数据身份 + 固定版本 + 按列和样本读取 + 可重建索引”的组合，而非直接将某一种格式确定为唯一主格式。
训练加载不能仅是 SQL 的 SDK 包装：需要单独定义数据集快照、样本顺序、epoch、随机种子、worker 切分、恢复 token 和保留策略。
多模态 blob 内联、旁置和外部引用应保留为物理布局选项；应根据对象大小、访问局部性、训练模式和重复引用比例验证。
索引补扫值得保留，但需要明确补扫上限与失败方式：索引长期滞后时，不能让一次检索悄悄退化为无预算全表读取。

## 4. Milvus：对象存储检索与外部湖查询的直接竞争参照

### 官方文档描述

- Milvus 当前架构将访问层、协调与工作节点、存储分开；Query Node 读取对象存储中的历史数据，Data Node 负责后台压实和索引构建，Streaming Node 处理流式数据及相关一致性工作。[架构说明](https://milvus.io/docs/architecture_overview.md)
- 对象存储保存日志快照、标量／向量索引及中间结果；元数据和 WAL 的职责另行定义。说明“使用对象存储”并不自动等价于“系统只需要对象存储”。[架构说明](https://milvus.io/docs/architecture_overview.md)
- 全文检索采用 analyzer 与 BM25，自动生成相应稀疏表示，并可与密集向量检索结合。[全文检索](https://milvus.io/docs/full-text-search.md)
- 文档定义 Strong、Bounded、Eventually、Session 等读取一致性选择；这些选项表达分布式数据可见性，不等同于用户业务的多表事务能力。[一致性说明](https://milvus.io/docs/consistency.md)
- 3.0.x 外部集合要求 Storage V3，可在不导入源数据副本的路径下建立源文件行与 Milvus 元数据之间的 manifest 映射，再建立索引；源发生变化时需要触发刷新。[外部集合创建](https://milvus.io/docs/create-an-external-collection.md)
- 官方 3.0 外部集合说明列出 Parquet、Iceberg、Lance、Vortex 等外部来源，并区分托管集合的在线变更与外部集合从 Milvus 侧只读的路径。具体格式版本、删除类型和源更新支持仍应逐项核实。[外部集合设计说明](https://milvus.io/blog/milvus-3-0-external-collection.md)

### 对本项目的判断

应将 Milvus 3.0 的外部集合纳入竞争基线，避免使用“向量库必须复制湖数据”的过时前提。
GuraDB 可借鉴外部源快照到本地索引 manifest 的映射，但需要更严格地定义源快照、稳定行身份、删除应用、刷新和索引就绪之间的关系。
元数据刷新完成不能在 GuraDB 中自动意味着全部派生索引可用于新快照；训练读取和检索应各自声明覆盖边界。
本项目已经收敛高并发 OLTP 与事务延迟目标，因此不应机械复制全部实时流式服务拆分；优先验证批量提交、分段索引和独立查询池是否足够。

## 5. Qdrant：可组合的检索接口值得借鉴

### 官方文档描述

- Query API 支持多路 `prefetch` 与后续主查询，可表达密集／稀疏召回、融合和多阶段重评分；相关入口自 1.10.0 起提供，后续新增选项有各自版本条件。[混合和多阶段查询](https://qdrant.tech/documentation/search/hybrid-queries/)
- 官方说明 RRF 与基于分数分布的融合方式，并提醒密集向量与稀疏分数不在相同尺度上；分布式集合中，融合放在顶层还是子查询会影响全局与 shard 内排序语义。[融合及分布式注意事项](https://qdrant.tech/documentation/search/hybrid-queries/)
- 自部署 Qdrant 的持久层要求块级存储与 POSIX 文件系统；官方安装文档明确该路径不能直接使用 S3 作为运行持久存储。此结论只针对该安装要求，不用于推断 Cloud 的全部内部实现。[安装要求](https://qdrant.tech/documentation/installation/)
- 官方将 payload 过滤、用户自定义分片及小租户共享／大租户独占的分层方案区分开；分层租户功能注明自 1.16.0 起。[多租户设计](https://qdrant.tech/documentation/manage-data/multitenancy/)

### 对本项目的判断

应借鉴“召回阶段 → 候选关系 → 融合／重排”的表达，而不是把混合检索限定成一个不可解释的加权函数。
SQL 与 HTTP 可以共享同一检索计划；计划应能展示每个分支的过滤、候选数量、预算、索引覆盖和合并位置。
RRF 可作为首批候选，但不能成为无需相关性评测的默认正确答案；分片剪枝、各 shard Top-K 截断和最终重排都可能影响召回。
Qdrant 可作为检索质量与接口可用性的比较对象；直接复用其整套自部署存储路径，则需要解决与对象存储湖主数据面的结构差异。

## 6. Weaviate：对象、模型与混合检索的产品体验参照

### 官方文档描述

- 一个 shard 包含对象存储、倒排索引和向量索引；这里的 object store 被定义为内部键值存储，其对象／倒排部分采用 LSM，不能仅凭术语把它当成 S3 式开放湖。[shard 存储组成](https://docs.weaviate.io/weaviate/concepts/storage)
- 混合检索结合关键词与向量结果，提供排名／分数融合方式和显式权重；文档提示客户端、服务端版本及默认值可能影响有效权重。[混合检索](https://docs.weaviate.io/weaviate/concepts/search/hybrid-search)
- 异步索引模式把向量索引操作放入队列；同步模式则随对象写入更新索引。自部署与 Cloud 有不同配置入口。[向量索引与异步索引](https://docs.weaviate.io/weaviate/concepts/vector-index)
- Weaviate 对集群元数据与数据对象使用不同的一致性方案；此分层有助于讨论控制面与数据面的取舍，但不宜照搬其全部复制协议。[复制与一致性](https://docs.weaviate.io/weaviate/concepts/replication-architecture/consistency)
- Cross-reference 允许对象之间建立引用；文档明确跨引用不会改变源或目标的向量。对象引用、向量图索引和通用图遍历是需要分别定义的能力。[对象引用](https://docs.weaviate.io/weaviate/manage-collections/cross-references)

### 对本项目的判断

可借鉴对象、多个表示和模型集成的产品体验；GuraDB 应进一步让每个表示携带生成模型、模型版本、维度、输入资产版本和转换参数。
默认值应在 SQL／HTTP 契约中固定并可发现；CLI 与 MCP 使用相同服务端默认值，不在客户端暗中改变排序权重。
GuraDB 的 Graph 检索需单独设计实体、边、方向、属性过滤和有界遍历，不能把 HNSW 的内部邻接关系当成业务图能力。
对象引用适合作为关系建模的参照，无法单凭该页面确认完整图语言、路径搜索或湖快照上的图一致性。

## 7. 建议细化的产品能力架构

以下是研究推导的能力划分，供主架构文档进一步确定优先级。

| 能力域 | 建议首批产品能力 | 必须明确的契约 |
| --- | --- | --- |
| 资产与片段 | 原始资产、文档块、图像区域、音视频时间片、样本组合 | 逻辑身份、模态坐标、原始引用和来源版本 |
| 湖连接与目录 | 外部表注册、快照发现、托管表、批量／微批导入 | 读写方向、源快照、schema 与删除语义 |
| AI 派生数据 | embedding、OCR／ASR、标签、实体关系等任务与产物管理 | 输入版本、模型与参数、重试、失败及回填边界 |
| 统一检索 | 关系过滤、全文、向量、多路召回与重排 | 候选集、评分来源、精确／近似边界、权限前置 |
| Graph | 版本化节点／边、邻居扩展与有界路径查询 | 最大跳数、展开预算、边版本和证据回溯 |
| 训练数据集 | 选择与去重、固定样本集、投影、批读、混洗与恢复 | 数据快照、排序／随机种子、worker 切分及保留 |
| 推理／Agent | 上下文检索、按实体取特征与媒体、长任务和取消 | 查询预算、版本和新鲜度、错误结构及可追溯结果 |
| 治理与运维 | 权限、租户、配额、血缘、审计、备份恢复、成本观测 | 元数据与媒体访问共同授权，索引就绪和删除传播 |

“推理”在首批产品中建议指模型周边的数据读取与检索；GPU 模型执行、特征实时服务和模型服务平台应另行确定边界。
“一体化”优先统一身份、快照、计划、权限和运维；不同检索模式仍可使用不同物理索引。
“兼容全部主流格式”应拆成可扩展适配器和逐版本能力矩阵，避免承诺所有格式都能任意原地写回。

## 8. 对象存储湖技术架构的建议取舍

这些是 GuraDB 设计建议，不是上述产品已经证明可直接复用的实现。

1. **持久数据面与可替换计算分开。** 原始资产、表数据、删除信息、manifest、索引产物保存到对象存储；查询节点的本地 NVMe 和内存承担可重建缓存。控制面元数据的权威实现另行选型。
2. **采用明确的发布边界。** 上传不可变文件后，通过可恢复的提交协议发布快照；未发布文件不能进入查询。重试、幂等和孤儿文件回收须与协议一起设计。
3. **快照先于索引。** 数据提交版本与各索引完成版本分别记录；索引元数据至少包含源快照／分段、覆盖行、删除应用版本、算法和模型版本。
4. **查询声明完整性策略。** 可选择固定就绪快照，或在预算内合并已索引数据与增量补扫；若预算不足则等待／报错／显式降级，不能静默漏读。
5. **删除优先保证可见性正确。** 旧向量、倒排命中和旧图边应经过所读快照的删除与权限校验；物理清理、历史保留与外部源删除必须分开定义。
6. **缓存按不可变身份寻址。** 使用对象版本／内容身份、表快照和索引 generation 区分缓存，避免同一路径覆盖导致旧字节混入新查询；适配不同对象存储时单独验证条件请求和一致性保证。
7. **训练与检索独立资源池。** 批量扫描、随机样本、媒体读取、索引构建各自限流，控制缓存污染与对象存储请求数量；独立资源池是逻辑能力，不预设每类必须独立服务。
8. **媒体取数延迟到需要时。** 初筛优先读元数据和表示，候选确定后再读取原文、blob 或范围；大视频的完整下载与片段读取须在预算上区分。
9. **控制面保持小而可靠。** 放弃高并发 OLTP 不代表目录可以多主冲突；提交指针、任务租约、GC 安全边界和权限状态仍需强约束。具体共识算法和元数据库待 ADR。
10. **格式层与系统语义分开。** 开放表／文件格式解决布局与互操作的一部分；跨格式统一身份、查询快照及派生索引发布由 GuraDB 负责。不得从支持某个文件读取推导出支持其完整表事务。

## 9. 差异化假设与下一轮验证

建议以以下可验收的流程验证定位，避免只做功能数量比较。

| 验证主题 | 建议实验 | 验收证据 |
| --- | --- | --- |
| 训练与检索共享版本 | 同一湖快照生成训练样本集与检索索引，持续追加期间重复读取 | 样本集合／顺序／表示版本可复现，追加不会混入固定数据集 |

| 外部湖变更 | 追加、更新、删除、schema 演进、源快照过期与文件重写 | 对每种格式／版本分别给出行为与限制，不用统一“支持”掩盖差异 |
| 冷热成本 | 冷缓存、热缓存、节点替换和训练扫描干扰下运行 | 端到端延迟、有效读取字节、请求数、缓存命中与重建时间 |
| 开放接口 | 同一计划通过 SQL、HTTP、CLI 与 MCP 执行 | 权限、结果、错误、取消及预算语义一致；PG 兼容单独分层验证 |

优先顺序建议：先打通固定快照的多模态数据集与文本／向量检索，再加入版本化关系和有界图扩展，随后扩展格式与分布式故障覆盖。
通用大规模图算法、毫秒级写后即查、跨格式原地分布式事务和高频单行更新不应成为首轮纵向切片的依赖。
保留面向应用的在线检索目标，但应根据冷／热缓存、数据规模和索引新鲜度分别确定 SLO；本轮不提出未经实测的延迟与吞吐数字。

本轮最应自行解决的部分是跨格式数据身份、快照／索引一致性、业务图与检索的共同计划、训练恢复语义及对象访问授权。
Lance 的读取布局、现有全文／向量算法和查询执行基础可以作为复用候选；是否引入、如何许可与封装，应经过原型比较与 ADR，不能由产品对照表代替选型。
