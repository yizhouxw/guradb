# 对象存储、湖格式与提交边界调研

状态：技术调研与建议，未实现。核验日期：2026-10-17。产品约束为对象存储湖架构、不承担高并发 OLTP、不承诺实时延迟敏感事务。

## 1. 结论

建议将对象存储作为业务数据与索引产物的持久层，以 **Iceberg v2 + Parquet** 作为首批托管结构化数据的基线，原始媒体作为不可变对象，Lance 作为首选验证的向量/随机读取物化层与外部数据源。所有逻辑数据有明确权威来源，避免维护两套独立提交的主表。

这是工程选择建议，不是性能实测结论。对象存储上的索引仍需要内存/SSD 缓存和请求合并；不用高并发事务内核，也仍需要可靠的目录提交、快照发布和恢复。

## 2. 已核实的事实与推论

| 官方依据 | 对 GuraDB 的推论 |
| --- | --- |
| Iceberg 使用快照、manifest 与元数据管理表，v1/v2/v3 已采纳，v4 仍在开发 | 首版固定 v2 子集以控制互操作面；不追随所有最新特性，也不以文件扫描代替表读取 |
| Iceberg 表提交依赖元数据引用的原子更新与冲突验证 | 复用 catalog 提交协议；不通过对象目录 LIST 或模拟 rename 实现事务 |
| REST Catalog 将发现、提交和授权委托放在接口后；多表事务提交是可选能力 | 面向 REST Catalog 接入，但不能假定任意 catalog 都能替 GuraDB 完成多表/多索引原子发布 |
| Lance 以版本化 manifest 管理 fragments、删除与索引；文件格式与表格式分离 | 可复用完整 Lance 数据集及索引生命周期；不能把索引文件拆出后假定可附着到任意 Iceberg 行位置 |
| S3 提供单对象强一致读写及条件请求 | 单对象条件写是构件，不是跨对象/跨湖事务；其他 S3 兼容后端需独立认证 |

依据：[Iceberg 规范](https://iceberg.apache.org/spec/)、[可靠性与并发提交](https://iceberg.apache.org/docs/latest/reliability/)、[REST Catalog 协议](https://iceberg.apache.org/docs/latest/rest-protocol/)、[Lance 表规范](https://lance.org/format/table/)、[S3 一致性](https://aws.amazon.com/s3/consistency/)、[S3 条件请求](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-requests.html)。上表右列均为本项目推论。

## 3. 托管存储方案比较

以下按本项目需求作定性判断，不构成产品排名或跨产品实测。

| 方案 | 优点 | 主要代价 | 建议 |
| --- | --- | --- | --- |
| 全部托管数据使用 Iceberg/Parquet | 开放表生态、明确快照、批量扫描、外部工具读取 | 多模态小范围随机读取和专门索引需额外布局 | 作为结构化事实数据基线，不把大媒体强行内联 |
| 全部托管数据使用 Lance | 版本化列式数据、随机读取、向量/标量/全文索引集成路径 | 对广泛湖 SQL 生态的适配和特性矩阵仍需补齐 | 保留为 AI 密集工作负载的替代 POC，不预先成为唯一格式 |
| Iceberg 与 Lance 双主、每次写入同时更新 | 能分别利用两者能力 | 跨格式提交、重试、删除、外部写入与恢复复杂 | 不采用首版双主路线 |
| Iceberg 事实层 + 可重建 Lance 物化层 | 开放事实层与 AI 访问布局分离，允许异步构建 | 向量/部分列重复存储，构建与刷新成本，需要稳定 ID 映射 | 首选验证；以真实成本和正确性门槛决定保留与否 |
| 自建完整多模态表格式 | 可按产品需要设计 | 长期读写兼容、事务、压缩、演进和生态负担 | 首版不采用；只定义必要的发布清单与图访问产物 |

Lance 的文件/表/索引能力见 [官方规范入口](https://lance.org/format/table/)；大二进制对象有独立 Blob 访问规则，见 [Blob API](https://lance.org/guide/blob/)。这不表示现有库能无成本满足上述物化方案。

Delta 与 Hudi 仍是重要外部格式。Delta 使用事务日志和乐观并发；Hudi 的 timeline、合并和表服务有独立生命周期。用户侧不追求高频点更新，减少了为写入新鲜度而优先选择这些机制的必要性，但不能据此认定它们不适用分析或 AI。[Delta 并发控制](https://docs.delta.io/concurrency-control/)、[Hudi 并发控制](https://hudi.apache.org/docs/concurrency_control/)。

## 4. 权威数据与派生数据

建议区分四类状态：

1. 原始资产：不可变媒体、文档或数组对象，使用稳定对象身份与独立校验值。
2. 事实表：资产、片段、业务记录、标签、关系和需要保留的特征结果，以明确表快照为准。
3. 加速产物：全文索引、ANN/Lance 物化数据、邻接结构、统计信息；能依据源快照和构建配置重建。
4. 发布清单：绑定事实快照与索引产物，形成 GuraDB 查询可使用的 read view。

训练所用 embedding 如果是不可复现或昂贵的模型输出，不能仅存在随时可丢弃的索引里。先保留特征输出及模型/参数版本，再构建 ANN。外部 Lance 数据集则以它自己的版本为事实来源，不为“统一”而强制转成 Iceberg。

不在数据表中保存真实存储凭证。短期签名 URL 是传输手段，不能作为资产永久身份。ETag 也不能一律当作内容 MD5；multipart 和部分加密方式有不同规则。[S3 对象完整性说明](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html)。

## 5. 原子性做到哪里

建议以三层可见性描述提交：

- **表提交**：对应格式和 catalog 的单表快照提交，失败/冲突按源协议处理。
- **数据集 revision 发布**：在 GuraDB 目录中，原子切换一个不可变清单的指针；清单固定组成表/对象的版本。
- **检索 read view 发布**：异步索引完成后，原子发布引用精确数据 revision 和索引清单的视图。

后两层是 GuraDB 自身的服务语义，不是 Iceberg、Lance 或 S3 自动提供的跨系统事务。分别提交的底层表可能被外部工具看到中间版本；GuraDB 的读者只有通过其目录才能获得 read view 的一致发布边界。首版不承诺跨外部表写入或任意外部读者的全局原子视图。

发布失败时，已生成对象、已提交但未发布的表快照和已构建索引必须能被对账；重试使用持久作业身份和预期旧版本校验，不能覆盖后来发布的数据。允许作业重跑，不允许重复发布相同逻辑写入而不报告。

## 6. 控制面与 catalog

建议 GuraDB 控制面使用独立 PostgreSQL 保存少量命名空间、权限、作业、版本指针、租约和发布状态，以小事务/CAS 协调发布。业务记录、向量、边和媒体不进入该元数据库；它不处于训练逐样本或向量逐候选读取路径。

这个决定与“不做业务 OLTP”一致，但意味着系统不是“只需一个 bucket”。元数据库需有独立 HA、备份与故障恢复；对象存储中的大清单和数据不能替代尚未重建的目录、权限和任务日志。

Iceberg REST Catalog 优先复用已有实现并封装适配层。Apache Polaris 是官方候选之一，需验证部署、授权、提交与运维要求；尚不在本轮锁定其为内嵌组件。[Apache Polaris 项目](https://polaris.apache.org/)。Iceberg Rust 官方项目可作为集成入口，其具体读写/删除特性必须通过版本固定的 POC 核对，不能从 Java 支持表推导。[Iceberg Rust](https://rust.iceberg.apache.org/)。

## 7. 对象存储访问与缓存

首版以 S3 API 为接入基线，通过适配层认证其他后端，至少检查范围读取、multipart、条件请求、对象版本/校验、重试、限流及权限。不能把“能连接 S3 endpoint”当作所有一致性语义相同。

建议采用内存元数据/热点缓存 + 本地 SSD 文件/范围缓存 + 对象存储持久层。缓存键包含源身份、版本和访问边界；不以可覆盖 URI 作为唯一键。跨查询复用缓存时，仍须检查当前授权。

Parquet 合理文件大小、行组、聚簇、列投影、请求合并、预取和批次读取应共同验证。具体文件大小由对象分布和测试决定；数百万独立小请求不能仅靠增加 worker 解决。大媒体保持外置，短小样本可在训练导出或物化层打包。

索引首次读取可以先把不可变 shard 文件下载到 SSD 后打开；按需远端页读取作为后续优化。必须测量冷启动、缓存命中、对象请求数、下载字节与重平衡预热，不能只测热缓存 QPS。

## 8. 维护、删除与恢复

小文件合并、数据重排、索引重建和快照清理由后台作业执行。不能直接按对象年龄删除文件；要检查已发布 revision、索引清单、活跃查询、训练 pin 和源格式保留规则。

Iceberg 的 snapshot expiration、orphan removal 与 data-file rewrite 是不同维护操作，且需要正确保留读取所需文件。[维护文档](https://iceberg.apache.org/docs/latest/maintenance/)。GuraDB 的发布层不能让源端 vacuum 在自己不知情时变得安全；外部源需要保留约定、托管复制或明确失效错误。

本轮不将 ANN/全文索引强行写入 Iceberg Puffin。Puffin 是可扩展的统计/索引相关 blob 容器规范，但具体 ANN 布局、语义和读取器互操作仍需定义，不会因为装进容器就成为通用索引协议。[Puffin 规范](https://iceberg.apache.org/puffin-spec/)。

## 9. 必须验证的工程门槛

| 验证 | 通过条件 |
| --- | --- |
| Iceberg 读写闭环 | 目标 Rust 库能读取选定 v2 表、正确应用 position/equality delete；生成的表可由独立官方生态工具核验 |
| 提交与恢复 | 在上传后、表提交后、发布前、发布后分别注入故障；重试不重复逻辑发布，既有视图不被污染 |
| Lance 物化 | 稳定记录 ID 与源版本可往返；追加、删除、压缩、重建不会混用旧候选；量化存储与构建开销 |
| 缓存/对象访问 | 数据量大于缓存后仍能正确完成冷热查询；限流与超时可控；缓存丢失可恢复 |
| 训练复现 | 固定 revision 下重复导出保持样本身份与模态对齐，外部源过期能明确失败 |
| 后端认证 | 除 AWS S3 外的后端单独运行语义与故障测试，不做笼统 S3 兼容保证 |

若 Iceberg Rust 的必需写入能力不能满足，先缩小托管写入特性或采用隔离的生态 writer 作业；避免为了尽快上线而悄悄忽略删除、双写主表或自研整个提交协议。
