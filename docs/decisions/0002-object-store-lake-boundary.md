# ADR 0002：对象存储湖架构与业务负载边界

- 状态：已接受（来自用户本轮明确的架构方向）
- 日期：2026-10-17
- 关联：[产品定位](../vision.md)、[功能架构](../product/functional-architecture.md)
- 补充：[ADR 0001](0001-project-scope.md)

## 背景

项目面向海量 AI 多模态数据。用户明确建议采用对象存储湖架构，放弃高并发 OLTP，不支持 RT 敏感型事务。本轮将此作为后续设计约束。

## 决定

1. 对象存储作为业务数据和持久索引产物的基础；计算与持久存储分离。
2. 核心工作负载为数据准备、批量/微批变更、训练读取、关系分析及多模态混合检索。
3. 不构建高并发 OLTP 数据面，不承诺严格低延迟业务事务、交互式多语句事务和同步写后所有索引立即可查。
4. 在线检索仍有响应时间与并发目标，后续按冷热缓存、复杂度和新鲜度制定，不能从“不做 RT 敏感事务”推导出无需优化查询。
5. 保留必要的原子快照、持久提交、冲突处理、权限校验和故障恢复。控制面的少量强一致操作不属于被放弃的业务 OLTP 负载。

## 解释边界

RT 在本轮按“对低延迟提交敏感的事务负载”解释，不排除 Agent/RAG 的交互式只读检索。若后续需要硬实时读取或毫秒级写后检索，则须重新评估新鲜度、索引和服务层边界。

不从本条需求推导“只需要一个 bucket”“完全无事务”或“无需强一致元数据”。具体格式、引擎和控制面实现属于[后续技术基线](0003-storage-and-execution-baseline.md)，并非用户直接指定。

## 影响与验证

优先设计不可变文件、快照发布、异步索引、缓存与批量访问。验证重点从点写 TPS 转向数据正确性、训练吞吐、检索质量、冷热成本、新鲜度与恢复；所有规模/延迟目标需要工作负载和测试证据。
