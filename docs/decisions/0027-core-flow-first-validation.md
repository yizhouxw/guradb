# ADR0027：核心数据流优先的分阶段验收

- 日期：2026-10-28。
- 状态：用户明确要求前期先跑通核心用例、把控资源模型和数据流，降低过早全面验证的负担；策略采用，执行器适配未实现/未验证。产品和CI暂停继续。
- 现行入口：[验收策略](../../harness/validation-strategy.md)。

## 原因

旧策略虽区分module/pair/system/release，但未登记的路径扩大system；文档基础检查也运行数据库合同服务。2026-10-28本次治理候选仅修改职责/模板/记忆，Issue表单文案仍触发system fallback；bootstrap因缺pyarrow等出现3 failures/12 errors，后续harness-tests阻断。这证明本次执行范围包含与治理无关的产品依赖，不证明数据库变更质量通过或失败原因均已定位。

在核心链路没有形成交付前，过早追求全覆盖、全组合和通用CI工具，会把工程活动变成产品前置，消耗上下文和跨角色沟通。此前门槛是当时决定，本次用户已调整阶段优先级。

## 决定与替代

采用“核心链路→功能强化→发布”：核心阶段验真实用户结果、资源所有权/生命周期/预算、固定身份版本的数据流及相关关键负例；定向测试随实际改动。全库覆盖率数值、全面故障/兼容矩阵、精细性能和长稳不作为首次核心用例跑通的前置。原80%/100%及完整发布义务保留在后续阶段，未验不宣称达标。

纯治理文档采用文档级验证；核心PR/精确main按本目标实际范围验证，不强制每次全系统39条。定向替代旧ADR0005/0007/0009/0015/0022与开发/CI规范中无差别前置的阶段安排；技术不变量、原失败、精确版本、普通Git流程和不绕hook不变。现有机器实现并未随文档自动变化，采用新profile需有限技术适配和独审。

拒绝“完全不测”和“先完成通用验证平台”两个极端。不新增数字覆盖门槛，不删除旧负例、不洗绿历史。未知残留、数据错误或失控资源仍阻断相应核心场景；规模目标仍需真实规模验收。产品部署、Actions开关和复工不由本ADR授权。

## 检验效果

下一个获准恢复的目标，观察核心用户路径是否实际跑通、资源与数据边界是否得到证据、从签收到可用结果的周期以及测试/工具前置时间。PM按交付结果调整排程，开发负责技术实施与验证选择，独验确认本范围结论；不以CI绿灯或文档数量替代产品进展。
