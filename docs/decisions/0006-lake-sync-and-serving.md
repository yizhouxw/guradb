# ADR 0006：湖加工结果同步与服务化目标

- 状态：已接受（产品技术目标经用户确认；详细协议和实现待设计/验证）
- 日期：2026-10-17
- 依据：Lakebase 借鉴讨论及用户要求将结论更新为项目产品技术目标
- 关联：[ADR 0002](0002-object-store-lake-boundary.md)、[ADR 0004](0004-snapshot-and-index-publication.md)
- 详细目标：[湖加工结果同步与服务化](../product/lake-sync-and-serving.md)

## 决定

1. 将湖加工结果到可查询 read view 的完整生命周期作为一等产品能力，覆盖源版本发现、初始加载、变化维护、索引构建和一致发布。
2. 同步可采用直接读取、选择性物化或完整托管导入；不强制复制全部数据，大媒体默认保持版本化引用。
3. 优先 Snapshot 与上游加工完成后显式触发的增量刷新；首批按可验证源/变更子集收敛。Continuous 为 P1，复用相同状态机，不引入实时事务承诺。
4. 以源提交而非通知或墙钟时间作为进度依据。行级变化流、稳定键快照差异和文件变化分别处理；压实不自动等于业务变更，历史缺口不能静默跳过。
5. 分开记录 discovered、applied、各索引 indexed 与 published 进度。只有数据和所需索引完整覆盖目标版本，才能原子发布对应 read view。
6. 大批量同步由后台生成存储/索引产物，遵循格式/catalog 提交协议，避免强制逐行 SQL 导入；提交结果未知先对账。
7. 同步表示不得形成双向多主。源湖权威的数据禁止客户端直接修改同步表示，应用状态与标注使用独立数据集。

## 边界

借鉴 Lakebase 的受控同步、批量存储直写及进度管理，不照搬其 OLTP 内核，不将 LTAP 或 Direct Writes 等同于任意外部湖表零复制接入。模式、格式、版本、变化语义和保留规则须分别验证。

此记录确定产品技术目标，不定义稳定 SQL/HTTP API，不修改已选技术栈，也不宣称已完成同步器、CDF、故障恢复或性能验证。沿用 GuraDB 目录内发布原子性，不承诺跨外部源全局事务。

## 后续验证

先证明固定快照初始加载、首条受限增量路径、更新/删除/压实识别和共同索引发布；再验证重复执行、结果未知、旧任务晚完成、源历史过期及同步/查询负载隔离。具体验收与预算见详细目标及[路线图](../roadmap.md)。
