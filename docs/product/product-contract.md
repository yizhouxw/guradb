# GuraDB 产品交付合同

日期：2026-10-19。状态：纠偏后的产品目标合同；下面的完整旅程均待实现验收。当前可操作白名单单列于[当前版本](../user/features.md)，不得由本文扩大。

## 1. 用户购买的价值

GuraDB 的交付对象是一个面向 AI 的分布式多模态数据库：让同一份版本化业务数据用于关系分析、全文/向量/图组合检索和训练数据准备，并可部署、授权、维护和恢复。对象存储与开放湖是持久基础；数据库负责身份、schema、查询、索引、发布、生命周期与治理。

用户不应承担把多套数据库、脚本输出和发布指针拼成一致系统的工作。接入已有湖表是一种入口；创建和管理数据库自己的数据集同样是产品职责。内部构建脚本可用于研发，不能长期充当正式写入和管理 API。

这是产品工作定义，不新增已经实现的承诺。非 OLTP、不做模型 serving、不提供训练调度平台的边界继续遵守 [ADR 0002](../decisions/0002-object-store-lake-boundary.md)。

## 2. 角色与共同工作空间

| 用户 | 用户任务 | 数据库必须提供的结果 |
| --- | --- | --- |
| 数据工程师 | 接入湖表/上传数据、登记媒体和处理结果、维护 schema 与版本 | 可查的接入进度、失败记录、提交版本和检索就绪状态 |
| AI 应用开发者 | 过滤、检索和关联原始证据，接入 Agent/RAG | 同一版本和权限下的有界结果、片段位置、来源与可解释排名 |
| 算法工程师 | 选样、关联标签、划分并固定训练集 | 可重复的样本与模态对齐、保留期限、导出及批次读取合同 |
| 数据库管理员 | 安装、授权、容量管理、升级和故障恢复 | 有版本的配置、监控、备份与恢复步骤、已验证部署边界 |

目标资源层级为 project/namespace → dataset → 数据/schema/revision/index/read view/job。project/namespace 的稳定外部命名、ID 与权限 API 尚待设计；当前 dataset UUID 不应冒充已完成多级资源管理。

## 3. 多模态是数据模型，不是向量列的别名

| 对象 | 最低产品合同 | 不能混同的对象 |
| --- | --- | --- |
| Record / Asset | 稳定逻辑 ID、版本、schema；媒体含可取的原始字节身份、类型与归属 | 文件路径、Parquet rowid、索引行号 |
| Segment | 父资产的确定版本、页/文本区间/时间/空间坐标及单位 | 与父资产最新版本动态关联的任意文本块 |
| Feature | 输入对象版本、处理器/模型版本、参数、输出 schema 与来源 | 每次查询重新生成且无法追溯的向量 |
| Relation | 带类型端点、方向、有效版本与证据；明确悬空边策略 | 字符串相同便认作同一节点 |
| Dataset revision | 精确的数据/schema/对象版本集合和保留责任 | 多个外部源的全局事务时间 |
| Read view | 可被一次查询共同绑定的数据和必需索引集合 | 各检索库各自的“latest” |
| Training dataset | 选样定义、样本/模态映射、split/seed、固定视图与 pin | 只含全部行的文件导出 |

一个资产可有多个版本；一个资产版本可有多个片段，一个片段版本可有多个模型空间的特征。关系端点必须说明引用资产还是片段。特征模型升级产生新版本，不覆盖旧训练任务所依赖的特征。跨模态检索须声明共享或可比较的 embedding 空间；两个任意向量列不能自动联合评分。

坐标、schema、空值/重复键和无键源等细则进入[数据合同](data-contracts.md)。这些对象允许以普通开放表表达，但用户操作、关联和校验不能依赖约定俗成的列名。

## 4. 六条产品旅程与验收

| ID / 旅程 | 用户观察的完整流程 | 必需成功断言 | 必需负例 |
| --- | --- | --- | --- |
| J1 建库与数据管理 | 安装 → 身份/namespace → 创建托管 dataset 或登记外部源 → schema/导入 → 发布 → 查询 | 不编辑内部 PG/产物目录即可完成；返回计数、版本、失败原因和索引状态 | 类型/重复键/不支持源语义拒绝；网络结果未知可对账；重放不重复提交 |
| J2 多模态知识检索 | 接入文本和图像 → 绑定片段/特征 → 过滤与混合召回 → 受限关系扩展 → 原始证据 | ID/版本、模型空间、排名、坐标及对象访问一致；无权限候选不泄露 | 模型/维度/父版本不符、对象消失、超预算明确失败；截断或近似性可见 |
| J3 SQL 数据准备 | 在固定视图过滤/投影 → 关联标签/资产 → 聚合检查 → 保存选择或导出 | SQL 与 HTTP 进入同一对象/视图/权限/类型合同；有独立关系真值 | NULL/int8/重复键、错误类型、未支持语法和未授权关联按白名单失败 |
| J4 训练数据消费 | 选样 → 防泄漏划分 → 固定视图和模型版本 → 导出/批次读取 → 释放 | 样本不丢不重、模态对齐、重跑一致；发布新数据不改变在途训练集 | 上游过期、保留不足、撤权、取消和 pin/GC 竞争可解释；不自动改为最新 |
| J5 增量与生命周期 | 发现/提交变更 → 构建索引 → 新视图发布 → 旧视图保留/回收 | 数据已提交和检索就绪分开；失败不影响旧合法视图；旧任务不倒退发布 | 更新/删除/rewrite/历史断链不能当 append；未知提交先对账；当前或 pin 引用不可回收 |
| J6 部署与恢复 | 单机评估 → 分布式部署 → 扩容/监控/备份 → 升级或恢复 | 安装产物、配置、容量和故障边界可复现；联合恢复后权限/对象/视图一致 | 多机丢片、目录故障、对象丢失、撤权补偿、旧格式读取失败分别有处置 |

首批多模态垂直验收选择**文本 + 图像及其片段/特征**作为设计默认值；这是本轮基于现有湖/向量基础的产品设计选择，尚无业务样本或质量预算。音频/视频的原始对象管理、时间片段、跨模态特征与读取逐模态验收，不降为永久不做，也不要求首片同时内建所有 codec/OCR/ASR。

## 5. 第一项产品闭环的准入范围

下一项实现应先完成 J1 + J2 + J3 的最小贯通，并为 J4 留出同视图消费：一个受控单机部署、一种托管批量接入和一种已支持的外部湖入口、文本/图像模型、固定视图、精确检索真值、可解释结果、同语义 SQL/HTTP、现有类型上的过滤/投影/受限关联。ANN 与大规模、多机不作为展示这个闭环的替代品。

允许分小片提交；第一片可只统一 dataset/read view 的绑定，再接对象与受控导入，然后接同语义查询。公开 API、DDL、查询扩展语法、错误码和迁移格式均须先形成版本化设计，再实现，本文不虚构已经可以执行的语法。

第一产品闭环完成也仅是单机预览；分布式 P0 和生产发布仍须满足[路线图](../roadmap.md)的 M3/M4。项目目标不因某次小片只支持一个输入而缩小。

## 6. 技术方案必须服从的产品门槛

- 单一目录绑定 dataset/schema/revision/read view/权限；前端协议不能选择不同事实源或另一套执行语义。
- SQL 的目标包括数据准备所需的关联与聚合，而不长期停留在单表查询演示；每个新算子独立验收。
- 索引只做可重建访问结构；每份 Lance/Tantivy/自定义产物必须有明确收益、所有者、兼容窗口与移除计划。
- Python 可保留控制/后台生态适配；在线查询经过共同计划与资源合同。是否迁移某算子以语义和成本证据决定，不以改写语言替代产品交付。
- 查询、批量训练和后台构建分别限额，但共享预算/取消/授权上下文。协调器不按全数据量持有业务记录。
- 生产工程与用户手册从首个闭环开始建设；高可用验收可以后置，其恢复/升级/授权设计不能到最后才补。
