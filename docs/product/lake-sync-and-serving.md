# 湖加工结果同步与服务化：产品技术目标

状态：产品技术目标已确认；同步器、接口、性能及故障恢复尚未实现或验证。日期：2026-10-17。

本目标承接用户对 Lakebase 方案的讨论结论，补充[产品功能架构](functional-architecture.md)、[技术架构](../architecture.md)和 [ADR 0004](../decisions/0004-snapshot-and-index-publication.md)。决定记录见 [ADR 0006](../decisions/0006-lake-sync-and-serving.md)。

## 1. 产品目标

将“湖加工结果发布成可查询数据”作为一等产品能力。上游加工引擎提交数据后，GuraDB 应能发现并固定源版本，完成扫描接入或物化、维护全文/向量/Graph 索引，并发布一致的读取视图，供 SQL、HTTP、CLI、MCP 和训练读取共同使用。

同步完成的标准是“目标数据版本及配置要求的索引已共同发布”，不是文件上传完成、变化已拉取或某一路索引已完成。沿用对象存储湖架构和非 OLTP 边界，不为同步功能引入高并发逐行事务或双向多主写入。

## 2. Lakebase 的借鉴范围

截至本次核验，Lakebase Synced Tables 将湖数据同步为 PostgreSQL 中的受控副本，提供 Snapshot、Triggered、Continuous 模式；增量路径需要可用的变化数据来源，当前文档也包括读时计算的 Automatic CDF。不能把同步能力简单限定为只有启用 Delta 写时 CDF 的表。[官方同步文档](https://docs.databricks.com/aws/en/oltp/projects/sync-tables)。

LTAP Direct Writes 是可选 Beta 能力：初始加载及 Snapshot 全量刷新可直接写入 Lakebase 存储层，绕过在线计算端点。它启发 GuraDB 将批量同步放在后台数据面，但不表示可以绕过目标格式的提交协议。[Direct Writes 说明](https://docs.databricks.com/aws/en/oltp/projects/sync-tables#accelerated-sync-with-ltap-direct-writes)。

LTAP 还描述了事务与分析共享逻辑数据的存储架构；这与把任意外部湖表同步成 PostgreSQL 表是不同层次，能力和可用性须按产品/云环境区分。[LTAP 架构](https://docs.databricks.com/aws/en/oltp/projects/ltap-overview)。

GuraDB 借鉴受控同步资源、批量存储直写、可观察进度和读取发布机制；不照搬 PostgreSQL OLTP 存储路径，也不承诺任意外部表零复制、任意格式增量或跨引擎全局事务。下述内容是本项目目标，不是对 Lakebase 实现细节的推定。

## 3. 同步资源与数据路径

建议以 `SyncDefinition` 表达长期同步关系，以 `SyncRun` 表达一次固定目标版本的执行。名称和字段是领域模型，尚未定义稳定 DDL 或 HTTP API。

| 契约 | 必须表达的内容 |
| --- | --- |
| 来源 | 源 catalog、格式/版本、稳定表或数据集身份、分支及源版本解析规则 |
| 映射 | 目标数据集、选取的列/过滤规则、身份/键策略、记录版本及类型映射；增量前验证稳定键 |
| 模式 | Snapshot / Triggered Incremental / Continuous，与触发来源分别配置 |
| 布局 | 直接读取、选择性物化或完整托管导入；原始媒体默认使用版本化引用 |
| 就绪条件 | 必需索引集合、模型/分词/图构建配置、完整性与新鲜度策略 |
| 运行约束 | 身份/授权、资源预算、源历史与依赖对象保留等级、重试/去重与发布规则 |

| 路径 | 产品用途 | 边界 |
| --- | --- | --- |
| 注册并直接读取 | 源布局适合扫描，固定版本可访问且能保留 | 不复制全部业务数据；仍可能生成索引、缓存和必要映射 |
| 选择性物化 | 改善向量检索、过滤、证据读取和随机回表 | 仅复制必要列及表示，绑定精确源版本，可重建 |
| 完整托管导入 | 源保留不可控、隔离需要或访问成本不合适 | 必须复制可复现读取所需的完整依赖闭包，含媒体及必要元数据/特征；只复制检索列不算完整托管 |

## 4. 刷新模式与实施优先级

触发方式与执行策略正交：一次上游完成事件可以触发全量刷新，也可以触发增量刷新；有事件通知不代表具备正确的行级变化流。

| 模式 | 行为 | 优先级与限制 |
| --- | --- | --- |
| Snapshot | 固定目标快照，完整构建新数据/索引视图，校验后替换发布指针 | M1 先做受限 Iceberg Snapshot；初始加载和无法安全增量时的恢复路径 |
| Triggered Incremental | 人工或上游作业成功后显式触发，从已发布基版本维护到固定目标版本 | M2 独立门禁：仅有已验证稳定键的 Iceberg append-only 历史链 |
| Continuous | 常驻任务持续发现提交，按预算聚合为批次，复用相同执行与发布状态机 | 后续独立门禁；不承诺逐行即时可查或实时事务 |

首条增量限定单源 Iceberg 加工结果的确定性投影/过滤，不要求任意 SQL 的增量维护。必须确认基版本到目标的祖先链、追加提交及键约束；更新、删除、压实/重排、回滚、换分支与不兼容 schema 变化先明确拒绝，或按已配置并披露的策略 Snapshot 重建。Snapshot 路径也只能读取已认证特性，不能把重建当成绕过删除语义的办法。多源 JOIN、聚合和更多变化类型后续分别认证。

加工完成事件只用于唤醒任务。正确性以源提交版本和持久进度为准，重复/丢失通知不能导致重复发布或静默漏读；显式刷新与版本对账提供恢复路径。内部定时监控不是首个切片的必需依赖，首个可运行 M0 仅需固定 manifest 扫描，无需提前实现同步资源管理。

## 5. 变化发现与身份

1. 有可信行级变化流时，按源协议读取插入、更新和删除，保留源提交及事件身份。
2. 只有快照时，按稳定逻辑键与记录版本计算差异，或者全量构建；源文件列表差异不能自动视作行级 CDC。
3. 压实、排序和分片迁移可能改变全部物理位置而不改变业务内容，不能据此制造业务删除/新增或更换资产身份。
4. 没有稳定跨版本键时，不承诺安全的逐行增量映射；普通固定快照扫描与跨版本检索身份保证分别处理。
5. checkpoint 绑定源身份、分支/历史链及不透明提交 token；不能用墙钟时间或假定 snapshot ID 数值递增来排序所有格式。
6. 变化历史过期、源回滚/换分支、键定义或不兼容 schema 变化时，停止推进并对账；需要重建时明确报告，不越过缺口继续声称增量完整。

以上是长期适配规则；首条增量只实现第 4 节的 append-only 子集，不因为能列出重写文件就声称支持 CDC。键的命名空间、空/重复键和无键源的快照内身份遵循[数据与查询契约](data-contracts.md)；无稳定键仍允许 Snapshot 扫描与全量构建。

多模态变化需要传播到相应片段、特征、全文命中和图节点/边。内容或模型配置改变时，原 embedding 即使逻辑 ID 相同也不能继续作为新版本的正确候选。

## 6. 执行、进度与发布

```mermaid
flowchart LR
    A[湖加工提交 / 显式刷新] --> B[解析并固定目标源版本]
    B --> C[初始快照或变化发现]
    C --> D[后台扫描接入 / 数据物化]
    D --> E[全文 / ANN / 图产物构建]
    E --> F[校验覆盖、删除与源版本]
    F --> G[原子发布 Read View]
```

初次加载固定源版本 V0。并行加载期间产生的新提交不混入本次快照：可以先发布 V0 再处理后续变化，也可以按已保留的变化历史追到明确 V1 后发布；两者都要记录准确边界，不能遗漏加载期间的提交。

大批量同步由后台 worker 生成目标格式数据和索引产物，依照格式/catalog 协议提交及发布，不要求全部经过逐行 SQL 写入路径。直接接入外部源时，数据接入进度表示版本/扫描清单已固定，不暗示已复制源数据。

| 进度 | 说明 | 不得混淆的状态 |
| --- | --- | --- |
| discovered | 已发现且准备处理的源版本 | 不代表数据已持久应用 |
| applied | 数据或源扫描绑定已持久确认的版本 | 不代表所有索引覆盖 |
| indexed | 每种索引/分片实际覆盖的版本及构建 generation | 不以单个时间戳代替全部覆盖证明 |
| published | 当前查询可使用的 read view 及逐源版本 | 不能提前推进到尚未完整发布的目标 |

checkpoint 只能在对应效果已持久确认后推进；查询用 published 进度而不是消费游标判断新鲜度。read view 指针及其 published 进度应在同一控制面原子操作中更新。重试依据固定目标、源事件身份和任务 generation 去重；不宣称网络传输的端到端 exactly-once。

例如目标为 V42，全文/向量已完成、图索引仍在构建，配置要求三路索引时默认查询继续读取完整 V41。各阶段只要求已经接入并配置的索引，M1 不以 ANN/Graph 就绪为依赖。可在不复制未变产物的前提下发布新视图，但必须验证复用产物对目标版本的覆盖；不能直接混用不同源版本的候选。默认查询从 read view 取得固定源版本，不在查询开始时重新解析源最新。

## 7. 写入权威、权限与保留

每份同步数据有唯一写入权威。湖侧权威的加工结果，GuraDB 只维护其服务表示，客户端不能直接更新该同步表示。应用标注/状态写入独立数据集，通过显式关联或合并规则使用，避免刷新覆盖应用写入。

完整托管导入不隐含写入权威转移；若需要接管为 GuraDB 原生可写数据集，应另行定义终止同步、切换权威和恢复流程。跨格式双向冲突合并不在本目标内。

权限撤销/强制擦除独立于数据版本发布生效，不能被旧索引或缓存绕过。保留登记为 `upstream-protected`（经认证的上游保护）、`managed-copy`（受 GuraDB 管理的完整依赖副本）或 `best-effort`（无法约束源清理）。查询/构建/训练所需的源快照、变化历史、原始媒体和必要特征都在保护范围内才可承诺复现；本地 pin 不约束上游 vacuum。摘要只验证内容，不能保留被覆盖的旧字节。只有部分列/向量副本时，仍需披露剩余外部依赖和失效限制，不能标成完整托管。

托管 GC 通过目录事务标记 `retiring` 并拒绝新 query/train/build pin，等待已有 pin、保留期和安全期，再调用格式维护协议；源仍引用的对象不得直接删除。外部源只按已认证保护/释放协议协调保留，失效后的重试保持原版本，不能改成最新后宣称原视图仍有效。完整规则见[技术架构](../architecture.md#11-故障维护与可观察性)。

上游分别提交多张加工结果表时，应提供完成清单或明确逐表版本集合，不能假定同一作业名或时间戳代表跨表原子提交。本目标仅保证经 GuraDB 目录发布的读取视图，不保证外部直接读取底层表时看不到中间状态。

## 8. 可观察性与验收目标

控制面应展示同步定义/运行身份、固定源版本、上述四类进度、各索引状态、重建/降级原因、最后成功发布、失败和可恢复位置。新鲜度分别观察源发现、应用、构建和发布耗时；同时记录积压、扫描/变化行数、对象请求/字节、存储放大和查询干扰。

| 验收场景 | 必须证明 |
| --- | --- |
| 初始加载期间源持续提交 | 初始快照固定，后续变化不漏，实际发布版本可解释 |
| 重复通知/重复任务/响应丢失 | 先对账再重试，不重复逻辑发布，checkpoint 不越过未确认效果 |
| append-only 增量及不支持变化 | 首条增量正确追加；更新/删除/纯压实等不误当新增，明确拒绝或按配置 Snapshot 重建；未来扩展分别证明维护候选/关系/特征 |
| 单路索引失败/旧任务晚完成 | 不半发布，不使当前视图倒退；旧完整视图按保留及授权规则服务 |
| 历史过期/schema 不兼容/源回滚 | 明确停止、重建或失败，不静默略过缺口 |
| 撤权与 GC/训练 pin 竞争 | 无越权数据或路径；retiring 后拒新 pin；不把本地 pin 当成源保留保护，不提前回收仍被合法引用的数据 |
| 同步与查询并发 | 测量构建/刷新对冷热查询、训练吞吐、召回和对象成本的影响 |

不在本目标中承诺固定同步秒数、吞吐或全格式覆盖。每个已支持的源和模式都须有版本/特性范围、真实正确性与恢复证据，并在测试前冻结新鲜度、资源和成本预算。
