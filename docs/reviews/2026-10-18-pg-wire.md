## 发现与修复

### P2：关闭 prepared statement 未清理关联 portal

初始实现的 Close(S) 仅移除 statements 中的 Arc，已创建的 portal 仍持有该 statement 和暂停结果。`Parse s → Bind p → Execute(p, 1) → Close(S, s) → Execute(p)` 因而仍可读取缓存结果，不符合关闭 statement 同时关闭其 portals 的[PG 协议要求](https://www.postgresql.org/docs/18/protocol-flow.html#PROTOCOL-FLOW-EXT-QUERY)。

已复查修复：`close_statement` 使用 `Arc::ptr_eq` 清理关联 portals，Close(S) 和未命名 Parse 替换均调用该函数。raw 客户端已增加 Close(S) 后继续 Execute 的探针，断言 portal 不存在（`34000`），本轮 PG functional 子 driver 已运行通过。该项关闭。

### P2：部分帧写入超时后可能追加错误消息

初始 `wire::send` 把 write_all 超时映射为普通 timeout；会话随后在可能已经发送一部分的帧后追加 ErrorResponse。结果发送 wrapper 已经处理该风险，但 Query 的 RowDescription、Describe/Parse/Bind/Close 等直接回复仍有相同边界。

已复查修复：网络写超时统一返回 `connection_closed`；会话和启动的普通错误分支不再向该连接追加 ErrorResponse。执行期取消/超时保持 `57014`，结果发送另有 10 秒总预算；发送中取消/超时关闭连接以避免损坏协议。此修复不改变 SQL、持久数据或资源预算。

## 其余检查与限制

- Describe 调用相同 SQL 白名单，按列上下文推断参数，不读取源对象；冲突或未知类型明确失败。结果列元数据与投影/别名对应。
- 参数 int2/int4/int8 长度/范围、bool、UTF-8、NULL 与 text NUL 边界有明确拒绝；输入 OID 归并不扩大 SQL 列类型范围。
- 连接、帧、入站消息队列、prepared/portal 数量和暂停结果有界；PG/HTTP 共用执行并发 semaphore 与底层扫描/解码/内存预算。输出超限拒绝而非静默截断。
- 每次查询执行、Describe、Bind 及暂停结果继续读取均重查授权；取消密钥绑定连接。portal 的保留时限是在 Execute 时检查，不宣称后台精确按时回收内存。
- 目前未发现新增阻断项，但完整生产隔离、远程 TLS、任意 pipeline、更多驱动/ORM 和整库长稳不在本片结论内。

真实测试发现共享文件系统中直接改写 auth_file 可能被并发读取为不完整 JSON；服务返回 `auth_unavailable` / SQLSTATE `58000`，没有继续使用旧权限。这是 fail-closed 行为。操作指南已要求在同目录完整写好临时文件，再原子 rename 替换，不能将非原子写入期间的错误当作授权绕过或测试成功。
