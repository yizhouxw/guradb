# 团队协作：模块责任与独立任务 Issue

状态：2026-10-24 用户已决定采用，2026-10-26 按用户要求明确 PM 管理边界；见 [ADR 0023](../docs/decisions/0023-team-issues-and-local-quality.md)。本文件是团队职责、技术升级与派发规则的唯一规范；根 AGENTS、harness 入口和调度提示引用本文件，不另复制职责规则。本合同规定组织与交接，不代表团队成员已全部到位或新增数据库能力。

## 角色与责任

| 责任位 | 唯一责任与交付 |
| --- | --- |
| 产品经理 | 用户场景、需求优先级、支持/拒绝白名单、可执行验收；定义做成什么 |
| 架构师 A | 模块边界、公共接口与版本、依赖 DAG、持久化/恢复不变量与 ADR；共同版本来源确认与跨模块技术争议裁决 |
| 模块开发负责人 | 本模块设计、实现、自测、缺陷修复和冻结后的消费者交接；对可消费成果负责到底 |
| 系统测试负责人 T | 独立真值、具名非作者技术复核、真实配对、端到端功能/性能/故障/恢复与发布验收；独立给出 PASS/HOLD/FAIL 及适用范围 |
| 集成与工程负责人 E | 共享构建环境、真实依赖、热点与共享文件、冲突合成、唯一串行 main 合入与精确主线核验；提供模块作者可用的共享工程入口 |
| PM | 目标与优先级、唯一 DRI、依赖、在制槽、共享资源窗与检查点排程、风险升级；接收具名独审结论、跟踪已验收交付并向用户汇总 |

PM 只做管理协调，不实现代码、编写 runner、执行测试或 probe、重算技术 hash、重构 diff 或逐行技术审查。PM 接收责任人给出的精确候选引用、结论、限制与下一动作，核对责任、依赖和验收出口是否齐备；技术结论由具名技术责任人承担，不由 PM 再做一轮技术复验。

技术疑义按责任直接交回：模块语义、实现与自测失败交模块 owner；公共接口、版本来源、边界与 DAG 争议交 A；独立真值、证据充分性与验收结论交 T；共享构建环境、依赖、热点写权与集成问题交 E。PM 指定对应 DRI、依赖、下一检查点并跟踪升级；同一人分时兼任角色时，仍登记本任务的实际角色与文件域，作者不能兼任该片独审。

每个核心模块设置一个稳定开发负责人：

| 模块标签 | 模块负责人负责的范围 |
| --- | --- |
| `module:catalog` | 身份/授权、目录、revision/view、发布、pin、操作状态与对账 |
| `module:storage` | 固定对象版本、传输、完整性、缓存、请求/字节预算 |
| `module:connectors` | 源版本、格式兼容、Parquet/Iceberg 读取、批次及接入适配 |
| `module:query` | 唯一 SQL/类型/参数语义、Arrow/DataFusion、执行、融合与回表 |
| `module:index` | BM25/向量/图索引、构建、覆盖证明、候选和定位 |
| `module:cluster` | 任务与 worker 生命周期、取消、背压、进程/资源控制 |
| `module:gateway` | HTTP/PG 会话与协议、统一客户端、CLI/MCP |

公共 `common` 合同由架构师负责维护，变更指定唯一作者；`module:common` 用于该类任务。工程门禁用 `module:harness`，专职系统验收用 `module:system`，产品/PM/跨模块集成用 `module:project`。标签定义与角色映射见 [模块标签清单](module-labels.json)，源码唯一归属与依赖仍以 [architecture.toml](architecture.toml) 为准。

逻辑团队共 12 个责任位（7 模块 + 产品/架构/系统测试/集成/PM），使用四个实际执行槽，同时至多两项行为开发，保留独立审查和系统测试能力。角色归属固定，按依赖与可验收交付调度；不要求成员用量或参与度相等，不按 credit 或活动量分配任务、衡量产出，也不为均摊而创造工作。具体人或 agent/session 在任务 Issue 中登记；未指定负责人即未派发，不能把角色表当作已启动成员。负责人更换必须显式交接，不能由历史 agent 名自动恢复写权。

每个任务独占声明的文件写域；共享文件和热点由 E 协调唯一写权，main 由 E 在集成窗口串行合入。重资源及性能/coverage/迁移窗口独占，PM 排定窗口，E 核技术参数与共享工程冲突，模块作者执行本模块自测。不能因共享环境由 E 供应，就把所有模块实现、自测或 oracle 转交 E；Issue 排程记录不冒充机器强制锁。

## GitHub Issue 是派发与交接入口

所有后续派给某个人或 agent 的工作均建立独立 Issue，包括产品、架构、模块实现、独立审查、系统测试、集成与阻塞解除。先查重；已有 Issue 覆盖同一责任人与验收出口时继续维护。#19 等总协调单仅汇总依赖与进展，不能代替成员任务。跨角色大任务拆成关联子 Issue，分别交付；跨模块实现指定主模块 owner，其余供应方另建依赖 Issue。

每个任务必须具备：

1. **责任**：一个主 `module:*` 标签、一个 `role:*` 标签、真实 GitHub assignee；正文登记唯一 DRI 的角色、姓名或完整会话 ID，以及独立 reviewer/消费者。GitHub 同一账号承载多个 agent 时，assignee 不替代正文 DRI。
2. **目标**：用户或消费者可观察验收、支持/拒绝范围、非目标；明确模块/配对/系统/发布层级。
3. **边界**：允许文件域、分支/worktree、原始 base、共享文件写权、资源窗口。
4. **依赖**：关联需求/ADR、blocked-by Issue/PR、输出消费者；没有依赖明确写无。
5. **下一步**：下一可验证动作、检查时间（含时区）、预期出口；失败给当前假设/证据与有限时间盒。
6. **交付**：关联 PR（例如 `Refs #任务号`）、本地实际命令/报告、head/最终 main SHA、复核发现、已知限制、恢复/清理与剩余事项。

使用 [任务表单](../.github/ISSUE_TEMPLATE/task.yml)；表单模块下拉框不会自动设置 GitHub 标签，PM 在派发前按 [清单](module-labels.json) 添加标签并核对负责人。缺主模块标签、DRI 或验收条件不得开工；这是协作规则，当前没有声称平台自动强制。标签说明负责人职责范围，不能以标签替代唯一作者或授权。

状态在 Issue 正文/评论记录：待派发 → 开发自测 → 待配对/系统验收 → 待集成 → main 已核验。阻塞保留原阶段并记录 blocked_since、原因、责任、下一动作与检查时间；关键变化及时更新，无变化不刷重复评论。未验收不关闭；重复/撤销项关闭时注明原因、替代 Issue 与现场，不能计完成。合入 PR 不自动关闭仍有系统验收义务的任务，优先 `Refs` 而非提前 `Closes`。

## 自测、独立系统测试与集成

产品给出可执行用户旅程 → 架构明确本片必要合同 → 模块负责人实现和自测 → 专职系统测试组织真实配对/端到端验收 → 集成者串行合入 → 精确 main 验证。

模块负责人完成本模块单元、真实后端功能/负例及适用的性能/预算/故障自测并修复缺陷。稳定接口交接包含源码/commit、支持边界、调用方式、精确报告和下一消费者；不把全部历史大包重复复制或复扫作为普通交接前置。

系统测试在接口稳定时提前准备独立 oracle 与真实用户旅程，负责跨模块同 view/ID/version、授权、总预算、取消传播、unknown 对账、进程回收、恢复与长稳。结果独立于作者总结，缺陷交回对应模块 owner；作者不能替代该片独立验收者。系统测试与产品共同判断用户出口，模块通过不能推导系统通过。

验证采用现有本地 harness 与实际脚本，按实际变更和风险选择；只因新增修改/失败/未解决风险补充验证。模块、配对、main 系统和 release 证据分别记账；不得删除原负例、缩负载/预算/strict 或把 missing 写成 PASS。当前 [GitHub Actions 已暂停](ci-cd.md)，本机自测、独审及精确源码证据是合入依据。

## 同账号多会话非作者复核交接实例

以单文件文档任务 [作者 #34](https://github.com/yizhouxw/guradb/issues/34) → [独审 #35](https://github.com/yizhouxw/guradb/issues/35) → [集成 #36](https://github.com/yizhouxw/guradb/issues/36) 为例，三个责任位共用 GitHub 账号 `@yizhouxw`。本节给出执行与记录方式；实际进度和结论以各 Issue、真实 PR 及其证据为准，不能因实例入库就计为演练通过。

| 责任位 / 独立任务 | 完整会话 ID | 交付与边界 |
| --- | --- | --- |
| 作者 / #34 | `01a16d6b-0c5e-7d33-932a-4bc6f679367d` | 独占任务分支/worktree，仅写 `harness/team-collaboration.md`；实现、自测、提交并交接真实 PR，不代签独审或自行合入 |
| 非作者审查者 / #35 | `01a16d6b-1b7e-7b40-a682-a6bdef3971f6` | 只读当前 diff、必要合同和证据，独立登记发现与结论，不改作者文件或 head |
| 唯一集成者 / #36 | `01a16109-3476-7532-8d46-7762c1fea2b3` | 核对同一候选及独审，按串行窗口合入并验证精确 main；不把分支通过当主线通过 |

PM 会话 `01a16c65-d8a8-7671-a89c-e1906e47f4ab` 在派发前核标签、assignee、完整 DRI、验收、文件域、依赖、消费者和资源窗口。Issue 创建、评论或状态变化只是交接记录，**不自动唤醒会话或授予执行权**；需要续接时由已获授权的协调者显式派发。实例身份用于核对本批任务，后续任务登记自己的实际 DRI，不能沿用旧 ID 推定授权。

交接中始终区分四个完整 SHA，不能只写分支名或“最新版本”：

| 字段 | 取值与用途 |
| --- | --- |
| `B` / original base | 作者 task receipt 的原始基点；后续提交、同步主线或补证不能缩短此范围 |
| `H` / current head | 当前真实 PR 的 head；作者报告、独审结论与集成 expected head 都绑定它 |
| `M` / main-before | 集成者临合入读取的主线；检查它已包含于候选，并核对主线未在检查后推进 |
| `G` / merge | 实际 merge commit；合入后在独立干净 worktree 对完整 `M→G` 范围验收 |

1. **作者交付**：从核对后的 main 建立独占 `codex/34-review-handoff-example` 分支/worktree，启动 receipt 固定 `B`。说明本片无数据库行为影响；按实际 diff 的 plan 运行适用本地 check，正常 hook 提交，再对原始 `B` 做提交后 check、task-finish/checkpoint。在真实 PR 写 `Refs #34`，回链 #35/#36，登记 `B/H`、文件域、实际命令/报告、receipt、checkpoint 和可取证据位置。报告只说明本次选定层级，不据文档自测宣称数据库或发布通过。
2. **非作者复核**：PM 确认候选就绪并派发 #35 后，审查者在 #35 和 PR 的 COMMENT 中写作者与审查会话 ID、PR 链接、审阅 `B/H`、实际读过的 diff/报告及范围。每项发现记录文件/位置、问题与影响、责任人和处置；无发现也写明检查内容与未覆盖项，再独立给出 PASS/HOLD/FAIL。作者的 task-finish review 文字仅是作者复核记录，不能替代这份非作者结论。同账号不能提交作者自批的 GitHub Approval；COMMENT 不冒充平台批准。
3. **发现闭环与 head 更新**：作者负责修复并记录发现→处置→证据的对应关系；已结项分支按[PR 流程](parallel-development.md)启动 follow-up receipt，保留 `B` 并验证完整 PR 范围。任何追加提交、冲突处理或同步主线产生新 `H`，旧报告/独审保留原义，不能自动用于新 head。审查者复核新 diff、处置与适用证据后明确登记新 `H`；未完成前保持待复核，不将旧结论复制成通过。
4. **串行集成与最终验收**：#36 获派发后核对依赖、单文件写域、当前 `H`、原始范围报告及绑定同一 `H` 的独审；记录 `M`，按[合入条件](parallel-development.md)以 expected head=`H` 执行 merge commit。`H` 或 main 变化就停止并回到同步/复核。取得实际 `G` 后按当时适用层级执行精确主线 check、checkpoint并确认远端 main；记录实际报告和限制，Actions 如实记 `PAUSED_BY_USER/NOT_RUN`。失败停止下一项集成，保留现场并走修复/revert 流程。PM 收到作者交付、具名独审与精确主线核验结论及其限制后才登记演练完成，不代做技术复验；未验收不关闭任务。

各 Issue/PR 可使用下列交接记录；占位内容须换成实际值，尚未发生的环节保留“待执行”，不得预填 PASS：

```text
作者/独审/集成 Issue 与各自完整会话 ID：填写实际值
PR / 分支 / 独占 worktree / 允许文件域：填写实际值
B / 当前 H / 实际审阅 H：填写完整 SHA；独审未执行则明确待执行
本地命令、层级、报告、receipt/checkpoint 与证据位置：填写实际值
独立发现 → 作者处置 → 审查者确认及结论/限制：填写实际记录或待执行
M / G / 精确 main 报告与 checkpoint / 远端 main：合入后填写，当前待执行
下一责任人、动作、检查时间（含时区）、未解决阻塞：填写实际值
```

**机器与人工边界**：harness 会校验其实现范围内的报告、源码/基点绑定、命令与日志、receipt/checkpoint；保存 review 文本不证明审查者身份或独立性。同账号多会话身份、独立阅读、写域/资源窗口及派发由 PM/审查者/集成者核对，本例没有新增自动身份认证、分布式资源锁、Issue 调度或 GitHub 强制 Approval，也没有改变本地质量门槛和 CI 暂停规则。

## 排程与升级

PM按[持续协调、按需唤醒与跨机器交接](pm-coordination.md)维护唯一当前状态和一个有效下一检查点。密集交接在当前回合有界推进；长等待先保存可恢复记录，再更新既有调度。Issue事件不自动派发，模板不构成调度器、全局锁或平台能力证明。

每个任务开工前确定消费者和 main 交付出口。稳定点目标 30 分钟内指定 reviewer/消费者；真实配对目标在下一可用资源窗口、两小时内启动。预计超时及时更新可执行排程；同一条件两次无新证据失败停止盲试，保留现场、定位根因或拆片。超过一个工作日阻塞必须明确重排或升级。

PM负责范围收敛：不能把已关闭诊断窗或未来工程工具重新变成当前交付前置，也不能把单个 helper 的局部阻塞扩大成全队前置；真实依赖仍由对应技术负责人确认。截止风险提前给事实、可选处置与影响；不得为赶期伪造 PASS 或隐去已知失败。模块、真实配对、系统通过分别报告，进展主要以已在 main 可复现的验收出口衡量，同时记录阻塞 owner、等待集成、验证耗时与首次通过率，不以活动量计完成。
