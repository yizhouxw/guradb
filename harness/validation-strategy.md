# 先跑通核心主链路，再逐步强化

依据用户2026-10-28的阶段取舍与[ADR0027](../docs/decisions/0027-core-flow-first-validation.md)。此页定义目标的验收策略，优先于旧文档把完整测试平台/覆盖率/全系统套件作为每个前期切片前置的安排。项目仍暂停；此决定不授权复工、启用Actions或发布。

**落地范围：文档与固定读取核心链路的有限选择器。** 纯Markdown/RST的auto检查只执行repository。`--stage core --core-flow fixed-read`只接受本包登记写域，生成`core-limited`报告；其它未知核心目标明确拒绝。默认强化与原module/pair/system/release义务保留，新增入口本身不表示产品用例已通过。不能用bootstrap、手填报告或跳hook冒充新阶段。

## 三个阶段，一个明确目标

| 阶段 | 必须证明的结果 | 暂不作为本阶段卡点 | 可声明的交付 |
| --- | --- | --- | --- |
| 核心链路 | 一条用户用例走真实产品入口、核心内核和必要依赖至可核对输出；守住本条链路的资源模型、数据流及关键失败 | 全库覆盖率数值、全部模块资格、全格式/协议/故障排列、跨版本矩阵、精细性能优化和长稳 | 只声明这条有界用例、实际输入和限制；不称完整系统认证 |
| 功能强化 | 扩展真实场景/格式/规模；补兼容、权限、恢复/并发/故障和适用模块回归；交付对应完整源覆盖证据 | 未进入本阶段范围的发布环境/全产品混合长稳 | 只声明本范围功能、质量与测量结果 |
| 发布 | 全部承诺范围、安全/迁移/恢复、真实规模、性能与长稳、受控构建部署证据 | 不以核心链路或模块通过豁免发布义务 | 只有本阶段真实验收后才能声称可发布 |

阶段由目标卡明确。开发可在包内完成必要修复和定向复验；不会因一次失败就降低该案例的输入或标准。出现影响数据正确性、资源失控或权限的风险，即使在前期也必须解决或明确拒绝相应用法。

## 核心链路验收最小集合

每个目标选一个能展示价值的纵向切片，不先要求七模块各自完成。TASK只需要以下事实及证据链接：

1. **用户结果**：真实入口/输入、独立预期结果和实际输出。典型路径是接入已选源→固定身份/版本→读取或处理→写出/索引（若本目标需要）→查询/检索→返回结果。未用到的环节不强塞进本目标。
2. **资源模型**：本目标的对象/版本/句柄/任务由谁创建、谁持有、何时释放；内存、并发、I/O/远程请求有实际边界。选择一个最相关的取消或失败场景，确认资源终态；未确认写UNKNOWN，不假写回收。
3. **数据流**：一份源事实、固定视图、身份/版本贯穿入口至输出；必要的转换、生产者/消费者和读写权威清楚。索引或缓存不能形成第二权威；选一项相关的错版本、缺输入或不支持行为验证明确拒绝。
4. **针对变更的质量**：适用编译/静态检查、直接受影响逻辑的定向测试、上述真实链路及关键负例；独立测试角色判断用例结果和资源/数据边界。文档或小改动不默认重跑全部数据库用例。
5. **准确结论**：输入规模、源码版本、实际执行、已知限制和未测项。核心通过与强化/发布未验证并列；构建成功、mock或工具自测不能替代真实链路。

数据丢失/损坏、错误版本可见、绕权、无界资源、失败当成功等不是可推迟的“细节”。详细指标矩阵、全组合和非关键优化可以按后续目标排程。对生产数据和不可逆迁移另走风险准入，不把早期试跑当正式上线。

## 规模、覆盖与历史证据

用户要求的公开图片/声音/视频50,000,000,000–100,000,000,000唯一有效原始bytes与清洗/打标/检索总目标保留。核心试跑可明确使用其中的有界真实样本，不能以样本通过宣称规模目标完成；规模验收排进相应后续目标。

已有Python全部自研生产源80%、Rust原适用源100%及原排除规则作为强化/发布的覆盖义务保留，**不再作为核心用例首次跑通的前置目标**。本轮没有创建更低百分比、删测试或伪造覆盖；未测/未达仍如实记录。具体强化目标启用哪些覆盖与回归，由开发依实际范围记录并由独验确认，PM不逐行/逐命令审批。

旧失败和旧报告保留旧合同；阶段调整不追认原HOLD为PASS。用于发布的性能数据仍须固定负载与环境，不能通过少读数据或降低召回换取“提速”。

## CI和合入的适配边界

- 纯职责、Markdown与非执行性Issue说明：目标是链接/格式/一致性和单独文档复核；不应触发数据库原生依赖、合同服务或全系统回归。API/schema、可执行配置、质量机器策略不能借文档名义走此档。
- 核心功能的PR与主线确认：验证同一精确候选的核心链路和受影响检查；不默认每次合入跑39条全系统命令。强化回归按稳定里程碑集中，完整发布另验。
- 固定读取核心入口通过`task-start --stage core --core-flow fixed-read`或对已有active receipt执行`task-stage --stage core --core-flow fixed-read`绑定；normal hook和默认plan/check沿用，原始base不变。无receipt的精确main检查显式给同参数和原始`--base`。core profile执行repository/policy/contracts、有限harness自测、变更Rust源fmt、四个受影响package的clippy/test及真实HTTP driver；范围、命令、源码和限制进入报告及checkpoint。源码/工具逻辑变化、缺失driver/日志或失败均不得结项。超出[有限白名单](../scripts/harnesslib/stages.py)拒绝，普通unknown映射仍扩大system。
- 核心报告只声明`core-limited`，不提升为system/main完整认证，不授予覆盖率、性能或发布资格。显式强化/发布检查使用`--stage hardening`及原层级参数，保留全部原义务与planned/missing。核心自测中的toy进程只证明工具闭环，真实HTTP/Rust证据及非作者复核仍由目标包给出。
- 适配之前保留可审源码/文档和真实阻塞，不改报告、不关闭hook、不绕过现有提交条件。完整测试的命令、超时、输入和历史结果保留；改变的是何时适用，不是把未运行写成成功。
- Actions/PR远端CI与部署开关仍暂停。验证策略决定和恢复开发/恢复CI是不同决定。
