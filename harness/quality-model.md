# 质量模型与变更分级

**2026-10-28现行阶段策略：** 先按[核心链路优先验收](validation-strategy.md)验证用户用例、资源模型与数据流；全面覆盖/回归/性能长稳分阶段推进。本页旧全面前置条款仅描述现有执行器或后续强化/发布义务，不再定义前期产品优先级。机器选择器尚未适配，不能把文档决定冒称工具已生效或绕过hook。产品/Actions继续暂停。

状态：harness 已实现；数据库运行时门禁待接入。质量包含功能正确性、性能/检索质量/成本，以及稳定性与恢复，三者不能互相抵消。

需求就绪、完成标准、任务 base/证据/复核和失败交接统一见[开发流程](development-workflow.md)；执行平台与发布分层见 [CI/CD](ci-cd.md)。自动选择门禁是最低义务，不等价于整个需求验收已完成。

## 风险与最小证据

| 变更 | 必需验证 | 额外审查 |
| --- | --- | --- |
| 文档/说明 | 仓库链接与格式、policy、harness 自测、现有 API 契约 | 已定需求/提案/实测状态是否正确 |
| HTTP/SQL 契约 | OpenAPI/正反例，运行时存在时加功能/组件性能/组件稳定性 | 类型/错误、只读、新鲜度、分页/取消与旧客户端 |
| 客户端运行代码 | 功能测试；Rust 时加 fmt/clippy/test | 结构化输出、身份、重试与取消语义 |
| gateway 运行代码 | 功能、performance-smoke、stability-component；Rust 门禁 | 只读约束、预算、权限、取消与入口开销 |
| 查询/存储/索引/控制面/分布式/连接器 | 功能、performance-smoke、stability-component；Rust 门禁 | 版本/发布/恢复、I/O/内存/复杂度、数据与索引兼容 |
| Cargo/锁文件/toolchain | Rust、功能、组件性能、组件稳定性 | 当前切片联编、格式升级、许可与资源变化 |
| 模块配置/schema/部署/迁移 | 按所属运行模块提升功能、组件性能、组件稳定性 | 不仅 `.rs` 会改变性能与正确性，配置默认值/并发/预算同样需要证据 |
| 发布 | 全部门禁、长稳/升级与恢复；必须已有运行实现 | 可回滚/升级边界、基线、兼容与已知限制 |

未识别的生产代码保守提升风险，并被归属检查阻止；不能把运行代码放入新目录以避开质量门禁。当前映射是保守起点，后续细化应记录依据，不随一次失败临时放宽。

plan 同时报告直接 affected_modules 和按允许依赖 DAG 反向扩散的 impacted_modules，不变量义务覆盖后者。当前采用潜在依赖的保守闭包，不把它冒充基于真实调用图的精确影响分析。

真实测试/benchmark driver 本身变更也触发对应 suite（tests/functional、integration、compatibility、performance、faults、soak 与 benchmarks）；不能因它位于 tests 下就只运行 harness 单测。`tests/performance/component/`、`benchmarks/component/`、`tests/faults/component/` 触发组件层，其它性能/故障 driver 触发完整层。完整层和 soak 始终是发布义务，不能因普通变更只测组件就宣称产品整体合格。

该分层修复首次组件依赖未实现整库的循环，依据 [ADR 0007](../docs/decisions/0007-incremental-delivery-and-gates.md)。各层 planned/missing 仍然失败，已有功能测试、完整 registry 与测量阈值保持。高风险改动按影响增加集成/完整实验，不以自动路径选择作为充分验证证明。

## 功能正确性

- PG18 支持子集采用独立 PostgreSQL 对照，不只看 parser；未支持事务/类型/函数明确拒绝。
- 格式样本由独立 reader/writer 对照，覆盖 position/equality delete、field ID、schema、重写与源过期。
- 精确向量/小图/单片全文作为真值；ANN、分片融合与图扩展不能以不完整结果换取速度。
- 训练验证样本身份、模态对齐、split、固定版本和恢复，而非只检查导出文件存在。
- 对版本映射、去重、排序、图环、分区和重试使用属性/随机测试，记录 seed；有了真实内核再引入 fuzz/sanitizer，不在空仓库伪造运行。

## 性能与成本

热点变更必须说明复杂度、远程请求、批量/逐行路径、内存上限和取消传播。检索至少同时看相关性/recall、p95/p99、GET、读字节与 RSS；训练看吞吐、请求、读字节和内存。混合负载验证训练/索引构建对检索的干扰。

基准区分 cold/warm/partial/over-capacity；固定工作负载、数据、并发、种子、环境与索引/过滤参数。同一次实验不改变数据或召回设置再宣称提速。性能比较只是门禁工具，不会自动生成负载或控制缓存。

组件 smoke 使用真实生产路径和适用的质量/时间/内存/I/O 指标，不要求尚未存在的整库混合负载。首次无基线时，按测量前冻结的绝对预算建立实测基线，记录 `baseline-established`；不得写成已通过回归比较或把 candidate 与自身比较。后续变更比较经审查的同环境基线。完整证据协议仍见 [evidence.md](evidence.md)。

初始相对预算：延迟/请求/字节/RSS 回退超过 10%、吞吐下降超过 5% 失败；recall 不允许下降。它们是启动时的回归审查阈值，不是产品 SLO，也不是统计显著性结论；真实 workload 需要事先冻结绝对目标。高噪声判为不可判断，保留报告后调查，不能不断重跑直到绿色。

## 稳定性

[faults.toml](faults.toml) 登记完整产品发布所需的 12 个场景，包括上传后崩溃、响应丢失、索引半失败、旧任务晚发布、失效源 writer、多 worker 丢失/重复、对象限流、GC/pin、源过期、撤权和高扇出取消。当前组件门禁验证已实现切片的真实失败与恢复，不能声称覆盖此完整列表；完整 `verify-stability` 不接受缺场景的子集报告。

真实 driver 必须运行注入和恢复，记录 worker 数、seed、观察结果和 trace；仅写 `passed=true` 不构成验证。校验器检查证据完整性与 trace 摘要，不能自动证明 trace 中的事件真的满足不变量。

发布长稳还需：持续混合负载、RSS/句柄/SSD/任务积压趋势，控制面与 worker 重启，备份恢复，数据/索引格式升级/回滚和资源泄漏。小型故障场景集不替代长稳或生产 SLO。

## 控制代码规模与上下文

- 生产源必须有唯一模块归属，依赖方向见 architecture.toml；公共类型层不得反向引用上层，不成为杂物目录。
- 大文件拆分应围绕职责/接口；600 行上限不能通过散落字符串、压缩一行或生成 wrapper 规避。复杂度和公开 API 仍需复核。
- 共享测试代码集中于测试支持层；不要借 dev dependency 引入反向模块依赖。
- 根 AGENTS 保持导航和全局不变量，模块 AGENTS 只记录本模块的风险与验证职责；长期决定放 ADR。
- 改动完成更新相关说明与契约，避免 agent 读取过时目录。检查器执行证据与工作计划分开，不把对话历史作为唯一事实。

## 不能绕过的失败

缺失 suite、未知基线、不同测量环境、缺少指标/场景、非有限数值、测试失败、执行超时、伪造/示例来源和运行中修改代码都不能记为通过。不得删除负向用例、降 recall、减数据/并发、换暖缓存或抬预算来让回归变绿。

质量门禁本身的削弱、baseline 更新、持久格式/提交协议变化需要在变更记录中给出旧/新证据、影响和替代方案，并经过独立复核。这里不增加日常开发的许可流程；改变产品边界时同步 ADR。
