# PM持续协调、按需唤醒与跨机器交接

状态：协作规则与静态记录模板；落实用户授权的持续协调方式。不新增数据库行为、API、调度服务、后台进程或自动化任务，不改变Rust目标、质量阈值、CI暂停及[PR流程](parallel-development.md)。平台配置由已获授权的PM执行，文档作者无此配置权。规则的执行责任见[团队协作](team-collaboration.md)。

## 1. 唯一执行权与恢复入口

项目PM协调Issue维护**一个可定位的当前状态记录**，本项目入口为[PM协调Issue](https://github.com/yizhouxw/guradb/issues/19)。PM更新该记录及其稳定链接，旧记录标明已被哪个版本取代；成员独立Issue仍保存各自任务与证据，不能由总表替代。动态任务、机器路径、调度ID和时间只进当前记录，不滚动写进本规则。

记录使用[交接模板](templates/pm-handoff-state.md)。它是数据示例，不是JSON Schema、加载器或自动检查器。初始字段故意为空；复制后必须填实际值并按第4节人工核验，未初始化模板不能派发、恢复执行权或当作已配置调度。文档落地不代表本项目当前调度已核验。

PM执行者以完整会话ID、机器ID、明确授权与`owner_generation`登记。角色名、相同GitHub账号、旧会话摘要或旧记录存在都不授予执行权。作者/审查/集成继续使用独立Issue、分支/worktree/receipt及唯一文件域；PM保持实际四槽与共享资源窗口，不以唤醒扩大写权。

每轮先读取当前记录、相关Issue实际进展与输入版本，核对本次执行owner、代际、调度归属和资源窗口。读取PR时核实际head；需要本地任务时先核task-status和工作区，保留dirty现场。不沿用旧游标、“最新分支”或旧PASS代替证据。

## 2. 当前回合推进与等待选择

1. 有可行动结果就立即检查输入、交接下一责任人、更新状态并继续本责任链；评审意见已到不因预定检查时间未到而空等。每项派发仍须独立Issue、具名DRI、范围、验收和授权。无新证据不刷重复评论，风险/交付/需决策变化及时记录。
2. 密集讨论、修订、评审和交接时，等待相关**已有会话**。每次阻塞等待不超过60秒，可分段并响应新输入；工具默认等待更长时显式收紧。每段返回后重判最新结果/ETA/截止，不高频重复读取或轮询无关任务。
3. 有依据预计5分钟内就绪时，继续当前回合的有界等待与可做工作。依据必须是具名owner的承诺或可定位进度，不把“希望很快”当ETA。未知ETA不能按短等待无限续接。
4. 只有**没有可行动项且有依据预计下一进展超过5分钟**，才按第3节保存状态、安排一次有效下一检查并结束回合。预计时间不明时走有限退避，不默认长睡或永久保持活跃。
5. ETA未知时，记录失联/阻塞owner与解除动作，最多按5→10→20分钟安排三轮检查；每次先重新求最早承诺/硬截止，更早者优先。20分钟一轮后仍无新证据则明确blocked、升级/重排或请求所需信息，不无穷重复20分钟。相关操作同条件连续两次无新证据失败时按[开发流程](development-workflow.md)停止盲试并定位根因，不能借退避重置失败次数。

检查时间取相关有效承诺、硬截止与本轮选定退避/ETA中的最早者。已到或逾期即当前处理，不安排在过去，也不擅自延长承诺。记录明确时区和带偏移的绝对时间；机器单调时钟、旧游标与本地相对分钟不能作为跨机器恢复凭据。

## 3. 只有一个有效next_check与调度

整个PM责任链只有一个有效`next_check_at`和一个调度标识/代际。不同成员的ETA可分别记录，但PM从中选一个最早检查点；不能按每个成员再建监控。一次唤醒先读当前owner/代际/输入状态，再决定推进、等待、更新既有调度或结束任务，不只查询一次就机械退出。

更新顺序由当前PM负责核对：

1. 保存当前记录、待输入版本/ETA依据、下一动作、下一检查和最晚承诺；拟更新标记为`update_pending`，在`pending_change`保存拟定检查时间/代际与意图证据，旧有效检查时间/调度代际保留，不先伪报已取消。
2. 核实平台现有调度ID/状态/归属；在同一调度上修改，不新建第二份。首次确需创建时先查重；创建/更新结果未知先查询对账，无法确认就保留unknown并指定人工兜底，不盲建新ID。
3. 回读实际保存的目标会话/计划/状态与ID，登记有效代际和证据；失败或无回读不能标active。提前完成时立即消费结果，更新原调度/代际；无后续责任时确认停用原调度，保存可恢复入口再结束。
4. 每次唤醒比对`owner_generation`、调度ID/代际与已处理事件。过时代际、重复事件或非当前owner只做核对/记录，不重复派发、写入或新建监控。若平台没有稳定事件ID，以当前任务/输入版本和已记录的动作判断重入，不能宣称精确一次执行。

这些是PM人工纪律；模板没有实现CAS、全局锁、自动代际fencing或exactly-once。周期调度可能在下一检查前触发：无提前进展且未到有效检查点时保持安静，复用原调度；到点后重判并连续推进。周期近似不能叫精确单次唤醒。

无法配置/更新或机器离线时，将状态标为`schedule_unknown`或`blocked`，记录调度owner、可定位恢复入口、最早检查/截止及具名人工兜底；没有可执行兜底要立即升级，不能无声结束后假定未来必会唤醒。

## 4. 轻量记录的必填语义

| 字段组 | 填写与拒绝条件 |
| --- | --- |
| `schema_version`、`record_revision`、项目/repo/协调及当前记录URL | 固定模板版本，修改递增记录修订；当前记录必须能从协调Issue找到，不仅保存在会话memory或函数store。未知schema先只读对账，不自动执行。 |
| `pm` | 角色、完整DRI、唯一执行会话与机器、授权证据、owner代际和active/handoff等状态。未指定或交权未确认，拒绝恢复副作用。 |
| `state`、`waiting_on`、`checked_at` | 当前阶段，等待Issue/角色/完整DRI、明确输入版本及证据、带时区检查时间；不是仅写“等结果”。 |
| `ready_eta`、`eta_basis`、`latest_commitment_at` | ETA可为null，但依据明确unknown或可定位承诺；最晚承诺/硬截止另列，不能用ETA覆盖原截止。 |
| `next_action`、`next_check_at`、`timezone` | 动作、唯一责任人、触发条件及一个有效检查时间；actionable不以未来next_check阻止即时推进。 |
| `schedule` | ID、机器/目标会话、effective/update_pending/unknown等实际状态、代际、回读证据、已处理事件引用。未配置不填假ID，unknown不写stopped。 |
| `handoff`、`blocked` | 旧/新owner和机器、旧调度停止确认、新owner接权证据；失联原因、blocked_since、解除owner/动作与人工兜底。 |
| `evidence`、`local_resources` | Git commit/PR/Issue URL与repo相对证据引用；必要摘要、来源机器及当前机器可取性。本机绝对路径仅作补充，不能是唯一入口。不可访问就标unavailable/unknown，不假称跨机可复现。 |

`waiting_on`和`evidence`数组中的对象是字段示例，可按实际增删；整个状态仍只有顶层一个next_check。禁止写token、凭据、用户数据、原始敏感日志或无限历史大包。可取性/摘要用于定位核验，不是不可篡改或异地备份证明。

## 5. 跨机器接管

1. 候选接管者先只读当前Issue/记录、实际任务/最新head、receipt/报告及资源与调度归属，确认链接可达；缺输入、旧head或本地资源不可取就记录具体缺口。旧机器路径不能直接照抄到新机器执行。
2. 当前PM显式提出交权，登记旧/新完整会话和机器、当前输入版本及拟变更owner代际；在协调Issue登记可追溯交权证据。候选者尚无新的副作用/派发权。
3. 由有权限者确认旧机器调度已停止/停用及在途运行归属，并记录平台回读/旧owner确认。只修改JSON中的状态或增加代际不能证明旧调度已停。
4. 新owner明确签收后才登记生效代际与唯一执行权，核实或更新原调度归属；平台无法迁移时，先确认旧调度停用，再由授权者配置唯一替代并登记关联。不得在旧调度unknown时直接激活另一份。
5. 旧机器失联或停止无法确认时，候选者保持只读，标handoff_blocked，交具名owner/用户确认隔离、调度停用或其它可核实接管条件；不宣称自动抢占/全局排他。保留截止风险和人工兜底，不以重新发起数据库任务“恢复”未知副作用。

本规则不搬迁数据/容器/凭据、不自动恢复旧writer，代码恢复也不撤销外部副作用。临时断线后的同机器上下文恢复同样重读当前代际与原task状态；若已交给别人，旧PM不能自行恢复执行。

## 6. 平台能力与证据层级

2026-10-24读取的[官方Scheduled tasks说明](https://learn.chatgpt.com/docs/automations)描述会话内周期调度、分钟级间隔和既有任务更新。该说明不是本机账户、执行时刻或跨机排他的验收证据。

| 能力 | 本片可报告的事实／所缺证据 |
| --- | --- |
| 同会话周期与既有任务更新 | 本任务授权输入报告现工具具备；官方文档支持该能力类别。PM实际创建/更新/回读的版本、目标、ID及结果须写当前记录，文档作者本轮未调用配置或验证真实触发。 |
| 精确单次唤醒 | 尚未取得本机工具实测证据，不承诺精确one-shot；有权限PM可在同一已支持周期任务上保守回退，仍须回读/去重与完成停用。 |
| Issue事件自动派发、自动身份/跨机锁、精确单次执行 | 本harness未实现，不由文档、代际字段或相同账号推导；显式派发与人工交权继续必需。 |

能力变化由PM核实际工具/平台、记录可定位证据并评审后更新用法；规则按“查询/更新既有计划、确认停止、核对运行”的语义描述，不依赖某个工具名、私有API或RRULE实现。没有某能力就如实保留限制与兜底，不为本任务新造调度平台或第二监控。

## 7. 七场景静态规则演练

以下为作者桌面演练：以合成相对时间T和模板字段逐例人工走第2–5节，核对预期状态/动作/拒绝；不等待真实分钟、不调用调度、不跨真实机器、不运行数据库。T仅用于表内推演，实际记录必须用绝对时间/时区。各例的“符合”只指静态规则核对，独立复核另交审查Issue。

| ID／场景 | 输入状态与事件 | 实际走查步骤 → 预期下一状态/动作与拒绝 | 作者静态结果／限制 |
| --- | --- | --- | --- |
| PM01 短等待 | active owner A，输入v1；DRI承诺T+3分钟，未到截止 | 核承诺来源→留当前回合，每段≤60秒→每段重判；若T+2就绪立即交接v1并继续。拒绝长睡、另建监控或重复派发。 | 对照2.1–3和3.4，符合；未验证等待工具实际唤醒时延。 |
| PM02 长等待 | 无可行动项，具名ETA=T+12，最晚承诺=T+10 | 先保存v1/ETA依据/owner→唯一next_check取T+10→更新并回读原schedule，确认恢复入口后结束。拒绝把ETA延长硬承诺，更新unknown时不新建。 | 对照2.4与3.1–2，符合；未执行平台更新/回读。 |
| PM03 提前完成 | waiting，原next_check=T+10、schedule S/g7；T+2输入v2到达 | 核真实v2→立即消费→原S重排g8并回读；责任结束则确认S停用。旧g7晚到只核对不重做动作，不创建S2。 | 对照2.1、3.2–4，符合；并非已测试提前触发或精确停用。 |
| PM04 超时/失联 | ETA未知，已检查T；依赖owner B，最晚承诺T+18 | 记录B及解除动作→无更早事件时检查T+5、T+15；第三轮本应T+35但承诺优先取T+18并升级。无硬截止的5/10/20三轮后仍无证据也升级，不循环20。 | 对照2.5与检查时间规则，符合；非真实35分钟长稳，操作两次同因失败另触发根因纪律。 |
| PM05 重复唤醒 | 记录当前owner A、S/g8且输入v2动作已处理；旧S/g7或同事件再次到达 | 先比owner/代际/输入动作→标过期/重复，仅记录/读对账；不重发同一派发、不重做写入、不建第二计划。无稳定事件ID仍按输入与动作对账。 | 对照3.4，符合；人工规则不证明平台exactly-once或原子排他。 |
| PM06 上下文恢复 | 本地摘要停在g7，协调Issue当前g8；PR head已更新，报告仍绑旧H | 读取当前记录/实际head/task-status→以g8和新H登记缺证据/下一责任，不复用旧PASS；已交权则旧owner只读。可行动项立即推进而非查一次就退。 | 对照1、3和5.5，符合；未模拟进程崩溃/实际receipt损坏。 |
| PM07 跨机器接管 | machine-A失联，接管候选B能读Issue/PR，但本地证据不可取、旧S停止unconfirmed | 先核输入与可取性→handoff_blocked，B保持只读，指定旧调度核实owner/兜底；取得停止证据及显式交权/签收后才升代际、唯一调度生效。拒绝凭旧路径/generation直接开第二份。 | 对照4–5，符合；没有真实跨机停止/接管实测或全局锁保证。 |

模板结构/链接和普通documentation门禁只验证其各自范围；七例不是调度器测试或数据库质量证据。实际报告/命令、B/H、非作者审查及精确main证据记录在本任务Issue/PR，不能把本表的静态符合预填成平台PASS。
